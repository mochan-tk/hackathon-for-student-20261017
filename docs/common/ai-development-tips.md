# Copilotと開発する3つの工夫

この教材では、**依頼の伝え方、判断に使う情報、実行して確かめる仕組み**を一緒に整えます。プロンプト → コンテキスト → ハーネスという言葉は、ここでは設計する範囲が広がる関係として扱います。3つは重なり合い、開発中はどれも使います。

| 観点 | 整えるもの | このリポジトリに入っている工夫 |
| --- | --- | --- |
| プロンプトエンジニアリング | 今回、何をどこまで頼み、どうなればよいか | 目的・範囲・完成条件・確認方法を含む依頼例、Planから実装への切り替え |
| コンテキストエンジニアリング | 判断に必要な情報を、必要なときに読める状態にする | 企画・作業・検証の3文書、画面PNGと遷移、必要な資料だけ読む指示、セッション間の引き継ぎ |
| ハーネスエンジニアリング | AIが実行・観察・検証・修正を進められる環境と流れ | 共通の起動コマンド、Dev Container、AppのRun、テスト、CI、失敗の記録、人による確認 |

これは各社共通の厳密な分類ではなく、教材を理解するための整理です。例えばSkillは必要な情報を渡す仕組みであり、繰り返す作業の手順でもあります。Copilot本体が持つ対話・ツール実行の仕組みに、リポジトリ側で資料・実行環境・検証方法を組み合わせています。

## 1. 依頼は「目的・文脈・制約・完成条件」を具体的にする

[OpenAIの開発向けbest practices](https://learn.chatgpt.com/guides/best-practices#strong-first-use-context-and-prompts)は、依頼の基本として **Goal・Context・Constraints・Done when** の4項目を挙げています。この教材では、Copilotへの依頼を考える手がかりとして使います。

| 項目 | 学生が考えること | この教材で使う情報 |
| --- | --- | --- |
| 目的（Goal） | 誰が、何をできるようにしたいか | 利用者の困りごとと、今回変える動作 |
| 文脈（Context） | 何を読めば判断できるか | 合意した企画の該当箇所、関係する画面・コード・エラー |
| 制約（Constraints） | 今回の範囲と、守る条件は何か | 対象外の機能、維持する仕様、選んだ実行場所 |
| 完成条件（Done when） | 何を確かめれば、できたと判断できるか | DoDに対応する入力・操作・期待結果 |

必要なら、これに**報告形式**（変更内容・確認結果・未確認事項など）を添えます。これは[OpenAIの一般向けPromptingガイド](https://learn.chatgpt.com/docs/prompting#prompting-overview)のOutputも参考にした教材上の補足です。「OpenAIが定めた必須の5要素」という位置づけではありません。

[各環境のガイド](../../README.md#はじめる)には、初回の計画・実装を依頼する文があります。4項目は抜けを見つけるための手がかりです。小さな修正では今回変わることを短く伝え、すでに共有した条件は参照で済ませます。毎回すべての見出しを埋めたり、長い指示文を貼り直したりする必要はありません。

例えば「締切アプリをいい感じにして」だけでは、何を変えるかと完成の判断が曖昧です。[締切管理の参考例](../examples/deadline.md)なら、次のように具体化できます。これは説明用の例なので、自分たちの企画に合わせて変えてください。

```text
目的：
締切の近い順に、次に取り組む課題を判断できるようにしてください。

文脈：
合意した docs/product.md の「期限順に一覧で見る」に対応する作業が対象です。
関係するコードとテストを読んで実装してください。

制約：
通知やログインは今回追加しません。確認はチームが選んだ実行場所で行ってください。

完成条件：
期限を10月22日、20日、21日の順に登録したら、20日、21日、22日の順に表示されることを確認してください。

報告形式：
変更内容、実行した確認、未確認のことを報告してください。
```

チームが決めた**利用者の結果**を伝え、必要な制約を添えます。実装する関数名や細かな編集順まで、毎回先回りして指定する必要はありません。曖昧さや複数ファイルへの影響が大きければPlanで相談し、小さな修正はその範囲で進めます。[共通の実装ループ](build-loop.md)を使ってください。

Appで編集しCodespacesで実行する場合は、この例でも[GUIで変更を渡す手順](../copilot-app.md#codespacesへ変更を渡して確認する)に従います。AIは確認コマンドを案内し、学生が返す結果を待ちます。

根拠：上記のOpenAIの4項目と、[GitHubのプロンプト設計](https://docs.github.com/en/copilot/concepts/prompting/prompt-engineering)が勧める目的・具体的な要件・入力と出力の例を、DoDと依頼例に反映しています。OpenAIの一般向けガイドも、必要な項目だけ使い、固定形式を必須にしないと説明しています。実装と確認結果を見て依頼を調整します。

## 2. 情報は正本を決め、必要な部分を渡す

会話が長くなっても、次のセッションが現在の決定を読めるようにします。

| 場所 | 役割と使い方 |
| --- | --- |
| [product.md](../product.md) | 合意した企画・DoD・対象外。仕様を変えたらここを更新する |
| [tasks.md](../tasks.md) | 今回の作業、依存、残りの作業。再開時に今どこまで進んだかを読む |
| [verification.md](../verification.md) | 実際の結果と証拠。達成・未達・未確認を分ける |
| [source/](../source/README.md) | 関係する企画メモ、画面PNG、操作・遷移。AIが開けないURLだけで済ませない |
| [copilot-instructions.md](../../.github/copilot-instructions.md) | 共通ルール、資料の場所、起動・確認方法への案内。企画全文や会話全文を詰め込まない |
| [prepare-project](../../.github/skills/prepare-project/SKILL.md)・[verify-goal](../../.github/skills/verify-goal/SKILL.md) | 企画整理や完成確認が必要なときに参照する手順 |

今回のDoD、関係する画面・コード、該当するエラーを渡します。新しい仕様と古い画面が矛盾していたら、その差を明らかにしてチームが決め、正本と画面・テストをそろえます。未入力欄や参考例、仮説を決定済みの事実として扱いません。

再開時には、3文書と現在のコードから「最後に確かめたこと、未完了、次にすること」を説明してもらいます。過去の会話を全部貼り直す代わりに、決定と証拠が保存されているかを確認します。PCとCodespacesを切り替えるときも、この文書をコードと一緒にGitで渡します。

根拠：[AnthropicのContext engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)では、限られた文脈に十分な情報を選び、必要時に取得し、記録を使って継続する考え方を扱っています。[VS Codeのガイド](https://code.visualstudio.com/docs/agents/guides/context-engineering-guide)も、短い共通指示から必要な文書を参照する構成を説明しています。

## 3. 動かす・結果を見る・直す、を繰り返せるようにする

この教材のハーネスに相当する部分は、次の組み合わせです。

| 仕組み | 役立つこと |
| --- | --- |
| Node 24・lockfile・[Dev Container](../../.devcontainer/devcontainer.json)・[App設定](../../.github/github-app.yml) | 起動方法をそろえ、AIにも実行方法を伝えられる |
| `npm run dev` | 画面とAPIを起動し、編集した結果を操作して見られる |
| `npm run check`・`npm run test:e2e` | 機械で確かめられる条件を繰り返し検証する |
| [runtimeテスト](../../tests/runtime.spec.ts)と、企画に合わせて更新・追加するテスト | 配信の基本動作を残しながら、自分たちのDoDを検証する |
| [Checkワークフロー](../../.github/workflows/check.yml) | 本番用コンテナでテストし、公開を有効にしたmainでは同じイメージを配置する |
| [失敗時のtrace・画面](verification.md#自動テストが失敗したら) | どの操作で期待と違ったかを調べ、修正に必要な情報を戻す |
| [別の学生による操作確認](verification.md) | テストの期待値自体の間違いや、使いにくさを見つける |

完成条件 → 実装 → 実行・観察 → 条件との照合 → 未達の修正、を繰り返します。結果は文書へ保存し、次の作業・セッションへつなげます。失敗したテストの期待値を都合よく変えず、コードの修正か、チームが合意する仕様変更かを区別します。

CIの公開・デプロイはテスト成功を前提にしています。一方、**PRのマージを必須チェックで制限する設定は、GitHub側で別途行うもの**です。このテンプレートだけでマージ制限や課金上限が設定されるわけではありません。Skillや依頼文も、セッション終了後の自動再開を保証する機能ではありません。

根拠：[OpenAIのbest practices](https://learn.chatgpt.com/guides/best-practices)は、適切な文脈・簡潔な共通指示・検証・繰り返す失敗の改善を組み合わせています。[Anthropicの長時間エージェントの設計](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)は、実行環境、進捗の引き継ぎ、実動作の確認を扱っています。各製品固有の自動化機能や記事と同じ性能を、Copilotで再現したという意味ではありません。

## 同じ失敗を繰り返したら、何を直すか

失敗の証拠を見て、原因に合う小さな改善を選びます。毎回すべてのルールやSkillを増やす必要はありません。

| 起きたこと | 改善する場所 | 改善できたかの確かめ方 |
| --- | --- | --- |
| 頼んでいない機能まで作った | 今回の依頼の範囲・対象外 | 同じ依頼を見直し、差分が対象に収まるか確認 |
| 古い仕様や画面で作った | product・画面・参照先 | 次のセッションで現在の仕様を読み取れるか確認 |
| 動いた機能が後の修正で壊れた | 不具合を再現するテスト | 修正前に失敗し、修正後に期待結果で成功するか確認 |
| PCでは動くがCIで動かない | 依存・環境変数・起動設定 | 失敗した環境で同じ確認を再実行 |
| AIの完了報告と実際の動作が違った | DoDと照合するテスト・操作・証拠 | 別の学生も同じ入力と期待結果で確認 |

直したことと確認結果は既存の[検証記録](../verification.md)に、残る作業は[tasks.md](../tasks.md)に残します。再発する共通の問題だけ、短い共通指示や再利用する手順に反映します。不要になったルールは整理します。

テストの成功は、テストで表した条件を満たした証拠です。スターターのテストだけでチームの企画が完成したとは判断しません。自分たちのDoDのテストと人の確認を追加し、利用者の困りごとが解決するかも確かめます。
